## Smarter product-relevance selection in web research

**Where:** `selectProductLinks(candidates, alreadyRead)` in `src/harness/adapters/web-research.ts:1345-1380`. Called from `runResearch` after it has already read the initial search-result pages and collected every outbound link it saw on them into one flat `productCandidates` array (see the "product hop" comment block in `runResearch`, a few hundred lines above the function itself).

**Exactly what it does today, mechanically:** walks `candidates` in the order they were collected (i.e., in the order the pages that contained them were read, then in the order the links appeared on each page — not sorted by relevance at all). For each one: parses the URL, skips it if already read or a duplicate, skips it unless the URL path matches `PRODUCT_PATH_PATTERN` (a regex for `/product/`, `/products/`, `/item/`, `/itm/`, `/ip/`, `/dp/`, or `/p/` in the path) or the visible link text matches `PRICEY_TEXT_PATTERN` (basically "has a `$` followed by a digit"), skips known non-result hosts, caps at 2 picks per hostname, and stops entirely once it has 2 total (`MAX_PRODUCT_HOPS = 2`). There is no comparison between candidates — it is a pure filter-and-take-the-first-2-that-pass, not a ranking.

**Concrete failure mode this causes:** mission goal is "queen bed frame under $300." Search turns up a results page linking to five different `/p/`-shaped product pages across three retailers: a $180 queen frame, a $650 queen frame, a $220 twin frame (wrong size), a $290 queen frame, and a $310 queen frame (just over budget). All five pass the regex equally — the function has no idea what "under $300" or "queen" even means, it only knows "this URL looks like a product page." Today it opens whichever 2 of those 5 happened to appear first in the candidates array, which depends entirely on page layout and read order, not fit. It could easily open the $650 one and the wrong-size one while skipping the $180 exact match, and nothing downstream would ever know it made the wrong call, because there was no judgment step to get wrong.

**Proposed mechanism, concretely:** when `selectProductLinks` (or a new function that wraps it) has more than 2 candidates that pass the existing regex filter, make one small model call before picking which to open: input = the mission's stated constraints (budget, size, style — whatever the planner already extracted into the node's objective/capability input) plus the filtered candidate list (each one's href, anchor text, and host); output = an ordered list of which 2 hrefs to actually open, or "none of these look right" as a valid answer. Keep the existing regex filter as a cheap pre-filter (no point sending 40 raw links to a model), only add the model call as a second pass over the already-narrowed candidate set, and only when there are more candidates than `MAX_PRODUCT_HOPS` — if there are 2 or fewer, there's nothing to discriminate between and the model call should be skipped entirely so the common case stays exactly as fast and cheap as it is now.

**Why it'd help:** closes the exact gap in the example above — the mission's own stated constraints (budget, size) currently never touch the product-selection step at all, only the initial search query does. This is the only place in the research pipeline where "which of several real options actually fits what was asked" could be decided, and right now nothing decides it.

**Status: shipped.** `selectProductLinksSmart` (`web-research.ts`) wraps `selectProductLinks`: below the hop budget it behaves identically (no model call, no cost change for the common unambiguous case); above it, one bounded `generateText` call (`gpt-5.6-terra`, low reasoning effort, 8s timeout, structured output validated against the real candidate hrefs) picks which to actually open, falling back to the plain deterministic order on any failure and respecting an explicit "none of these fit" from the model rather than overriding it. One real bug caught live before shipping: the original per-host cap of 2 (meant for the "just open pages" path) was also silently squeezing the candidate *pool the model gets to judge* down to two whenever they all came from one store's own category page — extremely common in practice — so the model never saw the other three. Fixed with a separate, wider per-host limit for the collection pass; regression-pinned. Live-verified against real Thuma candidates: correctly picked "Classic Bed $1,000" as the one true match for "a bed frame under $1200, not a nightstand or swing" out of 5 candidates that all passed the same regex filter equally. Full gate green, deployed.

## Composio only covers Gmail and Calendar — Docs, Sheets, Slack, Notion are all unwired

**Where:** every Composio action Cardea can call is defined in exactly two places that have to agree: `COMPOSIO_SAFE_READ_CAPABILITIES` and `COMPOSIO_APPROVAL_GATED_CAPABILITIES` in `src/core/contracts/safe-capabilities.ts` (each entry is `{ id, tool, toolkit }`), and `src/harness/adapters/composio-capability.ts`, which needs a matching `inputSchema` entry and a matching `descriptions` entry for every `tool` slug named in those two lists.

**Exactly what's wired today, the full list, nothing implied beyond this:**
- Read-only: `GOOGLECALENDAR_FIND_EVENT`, `GOOGLECALENDAR_FIND_FREE_SLOTS`, `GMAIL_FETCH_EMAILS`, `GMAIL_FETCH_MESSAGE_BY_MESSAGE_ID`.
- Write, approval-gated: `GOOGLECALENDAR_CREATE_EVENT`, `GMAIL_CREATE_EMAIL_DRAFT` (drafts only — the description on this one states outright "Cardea cannot send mail").

That's it. Six actions, two toolkits (`gmail`, `googlecalendar`). No Google Docs, no Google Sheets, no Slack, no Notion, no anything else, even though `PRODUCT_FLOW.md` names Slack and Notion as candidate toolkits Composio was meant to eventually cover. If a planned mission ever needs "write these notes to a doc" or "put this list in a spreadsheet," there is currently no capability for that at all — the model has nothing to call.

**A separate, real caveat on the six that DO exist:** the comment directly above the `inputSchemas` object in `composio-capability.ts` (lines ~22-27) says the argument shapes for the two write actions were written from Composio's documentation, not verified against a live account, because "this environment has no reachable Composio credential and the installed SDK ships no tool schemas to check them against." In plain terms: nobody has actually confirmed `GOOGLECALENDAR_CREATE_EVENT`'s and `GMAIL_CREATE_EMAIL_DRAFT`'s argument names (`title`/`startIso`/`endIso`/etc.) exactly match what Composio's real API expects. If they're subtly wrong, those two capabilities would fail at the moment a mission actually tries to use them, not before — this is separate from "add more toolkits" and should probably be checked first, since it's cheap to verify (one real Composio account, one test call each) and touches something already shipped as if it works.

**Concretely what adding one new toolkit action looks like, using "create a Google Doc" as the example:** find the exact tool slug Composio exposes for it (something like `GOOGLEDOCS_CREATE_DOCUMENT`, needs checking against Composio's actual catalogue, not guessed), add one entry to `COMPOSIO_APPROVAL_GATED_CAPABILITIES` (id `composio.googledocs_create_document`, tool the real slug, toolkit `googledocs`) since creating a doc is a write, add its `inputSchema` (title, body/content, whatever Composio's real argument names are) and its `descriptions` entry (stating plainly it's a write that only runs after approval, matching the voice of the existing six) to `composio-capability.ts`. Same pattern for a "read a doc" or "append a sheet row" action, just filed under the read-only or gated list depending on whether it writes anything.

**Why it'd help:** the mission graph can already plan around "gmail.create_draft" or "googlecalendar.create_event" as a real step because those capabilities exist; it currently cannot plan around "put this in a doc" or "put this in a spreadsheet" at all, no matter how obviously useful that would be for a mission that produces a list, a comparison, or a summary, because the capability simply isn't registered anywhere for the planner to see.

**Status:** parked, not scoped. Needs: (1) live-verify the two existing write actions' schemas against a real Composio account first, cheap and separate from the rest; (2) decide which new toolkit(s) to add first — Docs and Sheets are the ones the user specifically asked for; (3) look up each new action's real Composio tool slug and argument shape before writing the schema, not guess it the way the original two writes were.

## Splitwise as a Composio toolkit, for post-booking bill splitting

**What:** Composio's catalogue includes a Splitwise toolkit (create/read expenses, groups, balances — exact action slugs need looking up against Composio's real catalogue, not guessed, same caveat as every other unwired toolkit above). Wire it in the same way any new Composio toolkit gets added (see the entry above for the exact mechanical pattern: an id/tool/toolkit triple in `src/core/contracts/safe-capabilities.ts`, plus an `inputSchema` and a `descriptions` entry in `src/harness/adapters/composio-capability.ts`).

**Concrete use case that motivated this:** a mission that books something shared — a group trip, a dinner reservation, a shared purchase — currently has no way to close the loop on "now split the cost between the people who owe." Once a booking or purchase completes (a Shopify cart, a flight/hotel booking node, whatever), a Splitwise write step could create the expense and split it among named people, the same way `gmail.create_draft` closes a mission by preparing something a human still has to send.

**Where this fits the existing trust model:** creating a Splitwise expense is a write with real consequences for other people's balances, so it belongs in `COMPOSIO_APPROVAL_GATED_CAPABILITIES`, same tier as `gmail_create_draft`/`googlecalendar_create_event` — planned freely, never executed without the person approving that exact action on the canvas first. Reading existing groups/balances (to know who to split with) would be a safe read, same tier as `gmail_fetch_emails`.

**Why it'd help:** it's a real, common "last step" for exactly the kind of multi-person, multi-branch missions Cardea's flagship demo is built around (the relocation mission, a group trip) — right now that last step (settling shared cost) has no capability to land on at all.

**Status:** parked, not scoped. Needs the same three steps as the Docs/Sheets entry above: look up Splitwise's real Composio tool slugs and argument shapes, decide which actions are read vs. write, write the schemas and descriptions.

## Composio (and other) capabilities aren't directly callable through WebMCP today

**What exists now, precisely:** the 12 WebMCP tools Cardea registers (`src/webmcp/use-cardea-webmcp.ts`, via `context.registerTool`) are all canvas-control tools — `create_mission`, `inspect_canvas`, `update_mandate`, `approve_mandate`, `focus_node`, `redirect_node`, `set_node_state`, `resolve_approval`, `open_takeover`, `open_pages`, `list_missions`, `open_mission`. None of them is "send a Gmail draft" or "create a calendar event" — an agent driving Cardea through WebMCP can only reach a Composio action *indirectly*, by creating a mission whose plan happens to include a Gmail/Calendar step, then approving that mandate, then waiting for the harness to execute it server-side. There is no fast path from "the person asked ChatGPT to draft an email" straight to a drafted email without going through full mission planning first.

**What "everything should be WebMCP, that's the point" means concretely:** expose the individual capabilities themselves — Gmail, Calendar, and whatever gets added per the entries above (Docs, Sheets, Splitwise) — as their own narrow WebMCP tools an agent can call directly, the same way `resolve_approval` is callable directly today, instead of every single one requiring a full mission to be planned and approved first just to, say, draft one email.

**The one thing this has to preserve, or it breaks the product's actual thesis:** every write-shaped Composio action is currently approval-gated (`COMPOSIO_APPROVAL_GATED_CAPABILITIES`) — planned freely, never executed without the person approving that exact action on the canvas. `resolve_approval`'s own tool description already states the pattern to copy: it only fires "after explicit user confirmation," and mechanically it can only resolve an approval that's already sitting on the canvas waiting — the two-step structure (something creates a pending approval, a separate explicit step settles it) *is* the safety mechanism, not an honor-system comment. Any new directly-callable tool like a hypothetical `draft_email` must follow the same shape: calling it creates a pending approval card on the canvas (same as a planned mission node would), it does not draft the email itself. A read-shaped one (e.g. "check my calendar") can just return real data directly, no gate needed, matching how `inspect_canvas` already works.

**Concretely what this touches:** new tool registrations in `src/webmcp/use-cardea-webmcp.ts` following the exact existing pattern (name, description, inputSchema via the existing `objectSchema` helper, `annotations: { readOnlyHint }`, an `execute` function) — plus, for the write-shaped ones, a way for that `execute` function to create a real pending approval outside the normal "planner decided this node" path, since today approvals only come from planned/executed mission nodes. That routing piece (direct tool call -> real approval card, without a full mission graph around it) doesn't exist yet and is the actual engineering work here, not the tool registration boilerplate.

**One real caution, not a reason to not do it, just something to weigh:** DESIGN.md's original WebMCP design explicitly rejected "one broad tool" and "exposing every UI action" in favor of a small number of narrow, deliberate tools — the same instinct probably argues for starting with the highest-value 2-3 direct capability tools (draft email, create calendar event) rather than mechanically exposing all six-plus-future Composio actions as their own tools on day one, so the tool surface stays as legible to an agent as the current 12 are.

**Status:** parked, not scoped. Needs a decision on which capabilities go first, and the direct-tool-call-to-real-approval-card routing designed before any tool registration is written.

## The context wallet has no WebMCP path at all, not even indirectly

**What exists now, precisely:** the wallet (`src/app/app/_components/wallet/use-wallet.ts`) is client-side-only UI state, backed by `localStorage` under `WALLET_STORAGE_KEY`. A person picks which wallet card(s) apply before approving a mandate; that selection becomes `mandate.selectedContextCardIds`, which `context-compiler.ts` reads to scope budget/context into planning. No WebMCP tool touches it — confirmed by grepping every `.ts` file under `src/webmcp` for "wallet": zero matches.

**The mistake I made and corrected:** I initially said an agent could reach the wallet indirectly through `update_mandate`'s free-text instruction. Checked the actual implementation (`src/app/canvas/_data/live-mission-data-source.ts:499-537`) and that's wrong — `updateMandate` only appends the instruction as a new constraint string; it explicitly carries `selectedContextCardIds: current.mandate.selectedContextCardIds` through **unchanged** every time, no parsing, no interpretation. There is no path, direct or indirect, for an agent to change which wallet card applies to a mission today.

**Concretely what's missing:** a WebMCP tool (something like `update_wallet_selection`, following the exact same registration pattern as every existing tool in `src/webmcp/use-cardea-webmcp.ts`) that takes a list of context card ids and proposes them as the mission's `selectedContextCardIds`, the same way `update_mandate` proposes a constraint change today, for the person to review before they hit "Approve the mandate."

**Why this is safe to make freely callable, not approval-gated like a Composio write:** selecting a different wallet card doesn't grant any authority the person didn't already set up when they created that card in Settings — it's choosing which pre-existing, pre-scoped bucket applies to this mission, and the mandate as a whole (constraints, authority, budget ceiling, wallet selection together) still has to be explicitly approved before planning even starts. Same risk tier as `update_mandate` itself: a proposal shown for review, not an action with its own consequence.

**Why it'd help:** matches the same "everything should be reachable" thesis as the Composio entry above — right now, if someone asks ChatGPT (driving Cardea) "use my Travel card for this," there's nothing that call can actually do about it, even though the person clearly stated a real, in-scope preference.

**Status: shipped, scoped narrower than first planned, after actually reading `use-wallet.ts`.** The wallet turned out to be pure client-side React state (`useWallet()` in `board.tsx`), completely separate from `MissionSnapshot`/`mandate` except for a one-time copy into `selectedContextCardIds` at `createMission` time. `updateMandate` was re-confirmed to carry `selectedContextCardIds` through unchanged (`live-mission-data-source.ts:527`), so there is still no path to change a mission's wallet selection once its mandate is open — that would be a mandate-semantics change with its own approval question, out of scope here. What shipped instead: a `toggle_wallet_pass` WebMCP tool that calls the wallet's own `toggle(id)` directly (a pure client action, same tier as `focus_node`/`open_takeover`, not a `dataSource` call), for selecting passes *before* a mission is created; and `inspect_canvas` now reports a `wallet` array (`{id, label, domain, selected, loadedUsd}` per starter pass) so an agent can see what exists and is selected before proposing a toggle or a `create_mission` call. New pure helper `toWalletPassSummaries` in `board-mission-actions.ts`, tested (6 new cases). Live-verified against the real running `/app` board (not just unit tests): registered a fake `document.modelContext` via Playwright's `addInitScript` (real Chrome's WebMCP API isn't available in stock Chromium), confirmed `toggle_wallet_pass` shows up alongside all 12 existing tools, confirmed `inspect_canvas` reports the 5 real starter passes with correct initial selection ("Personal" selected, rest not), toggled "Work" through the tool and confirmed `inspect_canvas` reflected `selected: true` after a render tick, toggled it back off, and confirmed a bogus id returns `unknown_wallet_pass` without mutating anything. Full gate green (tsc, lint, 334+465+65 tests, build), no regressions.

## Ratings and review counts have no structured extraction, unlike prices

**Where:** `PAGE_READ_EXPRESSION`, the JS snippet run inside every page Cardea's research/lookup capabilities read, in `src/core/browser-run/protocol.ts` (~line 504-535). This is the one place page content gets turned into structured data before coming back to the harness.

**What prices get, that ratings don't:** the snippet regex-scans the page's **entire** flattened text (not the truncated excerpt) for dollar amounts and returns them as their own `prices: string[]` field, separate from the excerpt — the comment right above it says why: "a buying brief without observed prices cannot recommend responsibly," so prices are deliberately load-bearing and protected from truncation loss. There is no equivalent for a star rating or a review count. Both only survive at all if they happen to land inside `text: flattened.slice(0, MAX_PAGE_EXCERPT_CHARS)` — the same hard character truncation that, applied to product URLs a few turns ago, was the exact root cause of "opened ikea but didn't find the exact bed" (real evidence existed, got silently cut by a length cap before anything downstream ever saw it). A rating that appears past that cutoff on a long page is just gone, no different from how those product URLs used to be.

**Concrete failure this causes:** a restaurant or product page states "4.6 stars, 1,240 reviews" somewhere past the first `MAX_PAGE_EXCERPT_CHARS` characters (easy on a page with a long description above the rating widget, which is common). The consolidation step never sees it, so a review-dependent recommendation (the exact case `context-compiler.ts`'s planning rules call out for restaurants and personal care) has to write "reviews look solid" or similar vague language with nothing to actually back it, or omits review strength entirely, even though the page genuinely had a specific number.

**Proposed fix, same shape as the fix already shipped for prices/products:** add a second regex scan over the full `flattened` text (same pattern discipline as the price regex) for rating-shaped tokens — something like `\d(\.\d)?\s*(out of|\/)\s*5\b` or `\d(\.\d)?\s*stars?\b` for the score, and a separate pattern for review counts (`[\d,]+\s*reviews?\b`) — bounded the same way prices are (a max count, dedup), returned as its own field alongside `prices`. Small, additive, no architecture change: same function, same extraction discipline, one more field on the same return object.

**Why it'd help:** closes a real gap in exactly the categories the planner is already told to seek review signal for (restaurants, personal care, "recent review signals") — right now the planner asks for that signal, but the extraction layer has no reliable way to preserve it once the page is read, so the ask is often unmet by construction, not by bad luck.

**Status: shipped.** Verified live against a real Thuma product page before writing the regex (`4.9/5`, `Overall Rating 4.9 (20,683)`, `21k Reviews`), not guessed. `ratings: string[]` threaded through `PAGE_READ_EXPRESSION`, `PageRead`, `readPageEvaluation`, `web-research.ts` (the ranking signal, both `results.push` sites, `boundResearchOutput`), and `execute-node.ts`'s upstream-evidence formatting. Live end-to-end proof through the real pipeline: a research run surfaced real ratings from Forbes ("19,000 reviews") and Mattress Clarity ("4.8 / 5") on genuinely different sites. Full gate green, deployed.

## No bridge between "web_research found a Shopify store" and "actually query its Shopify MCP"

**The platform limit first, so this isn't mistaken for a Cardea bug:** Shopify's storefront MCP is per-store by design — `www.thuma.co/api/mcp` only ever knows Thuma's own catalog. Shopify does not expose any global "search every Shopify store" API for MCP to call. There is no way to fix "make it know all Shopify stores" because that capability doesn't exist anywhere to wire into.

**What Cardea has, precisely:** one env-configured default store (`CARDEA_SHOPIFY_STORE_DOMAIN`, currently `www.thuma.co`) plus a per-call `store` override on every Shopify capability (`src/harness/adapters/shopify-capability.ts`, `overrideStoreDomain` in `shopify-mcp-client.ts`), built and live-verified earlier this session — the planner *can* target any other Shopify store by name, as long as it already knows that store's exact domain.

**The actual gap, confirmed by grep:** searched every file under `src/harness` for anything that detects "this URL is a Shopify store" — nothing exists. When `cardea.web_research` finds and reads a page that happens to be hosted on Shopify, nothing recognizes that fact; it just gets treated as a generic page, its text scraped into the excerpt the same way a WordPress blog or a hand-rolled storefront would be. The real, structured commerce data (exact price, variant id, cart-ready state) that the Shopify MCP could return for that exact same store sits one API call away and never gets reached, because nothing connects "found this domain via search" to "also hit its `/api/mcp`."

**Concretely what a fix looks like:** after `runResearch` returns its ranked results (see the ranking entry above — this would slot in right after that), check each result's host for a Shopify signal — the cheapest reliable one is probably requesting `https://{host}/products.json` (a standard endpoint every real Shopify store answers, used for exactly this kind of platform detection) or checking the page text/headers already captured for a Shopify tell (`cdn.shopify.com` asset URLs are a strong signal and would already be sitting in the page text pulled during the normal read). If a result's host looks like Shopify and the mission is a buying/booking one, automatically issue a `shopify.catalog_search` or `shopify.product_details` call with that host as the `store` override, so the mission ends up with real structured price/variant/cart data for that store instead of only scraped text, without the planner having to already know the domain in advance or manually decide to try the override.

**Why it'd help:** this is what would make the per-call store override (already built) actually get exercised in practice beyond the one hardcoded default — right now it technically works but nothing ever triggers it unless the planner happens to type an exact store domain into the `store` field unprompted, which isn't a realistic thing to expect from a model that just read a page, not a structured "detected Shopify" signal.

**Status: shipped, and the detection method changed from the original plan.** `products.json` was tested live first, per the "test both before committing" note above — and it failed for Thuma (404, custom storefront front-end, even though its real Shopify MCP works fine) while passing for Allbirds, so it was rejected as unreliable. Switched to a simpler, more direct design: no separate detection probe at all — `enrichTopResultWithShopify` (`web-research.ts`) just attempts the real `shopify.catalog_search` capability call against the top-ranked result's host directly (gated on that result already being a specific product page with an observed price or rating), and treats any failure as "not Shopify," silently. Verified live against Thuma: real UCP catalog data (merchant name, payment config) now flows into the research evidence. One real bug caught by that same live check before shipping: the enrichment was being silently truncated away by two independent excerpt-length caps that both assumed the base excerpt had room to spare, which it usually doesn't — fixed in both places, with a regression test pinning it. Full gate green, deployed.

## Memory only ever gets proposed from one hardcoded moment in one mission type

**Where:** the entire memory system is `src/harness/adapters/supermemory.ts` (the Supermemory client: `searchUserMemory`, `promoteUserMemory`, `forgetUserMemory`, `updateUserMemory`, each scoped to a per-user `containerTag`) plus `src/harness/adapters/memory-retrieval.ts` (`retrieveMemoryForContext`, which wraps search for planning use).

**How retrieval actually works, precisely:** happens exactly once per mission, in the `retrieve-memory` Inngest step (`src/harness/inngest/functions.ts:256`), run in parallel with capability discovery at the very start of `planMission` — before planning, never again after. The search query is the raw mission goal text (`data.goal`), not anything that evolves as the mission runs. Results feed into `PlanningInput.memories`, which `context-compiler.ts` folds into the planner's context, sorted by relevance and capped at 10.

**How promotion (writing a new memory) actually works, precisely, and this is the real gap:** grepped every call site of `onRemember` and `/api/memory/promote` across the app. There is exactly one: the "remember i liked X" button inside `ConciergeClose` (the buying-mission closing bubble), wired in `board.tsx:1384-1399`, calling `/api/memory/promote` with a single hardcoded fact shape — `"Preference: liked {topPick.label} when choosing in a mission."`, `source: "concierge_close"`. Nothing else in the harness, planner, or execute-node path ever proposes a memory. A flowers mission where someone picks "Peonies" over "Roses" and "Tulips" on an approval card, a research mission that surfaces a real stated preference, any correction made mid-mission — none of it reaches memory, because nothing generates a proposal from those moments. The sticky-note memory UI DESIGN.md describes (proposed near the canvas edge, Edit/Forget controls, promoted only on explicit confirmation) also doesn't exist anywhere in the real product — `MemoryVignette` in `src/components/landing/vignettes.tsx` is a decorative landing-page mockup only, not connected to anything live.

**Why this matters, concretely:** DESIGN.md's actual framing for this feature is "Cardea notices what your missions reveal... and asks before keeping any of it," from any mission, any moment a real preference surfaces. What's built is the opposite shape: reactive, from one specific ending of one specific mission type. The buying-close case works and is real (it's a genuine `POST /api/memory/promote` call, not a mock), it's just the only door.

**Proposed generalization, concretely:** the exact same pattern the buying close already uses (resolve a decision -> extract a preference-shaped fact -> offer a one-click "remember this," never auto-save) generalizes cleanly to any resolved approval, not just the concierge close. When an approval resolves (`resolve_approval`, or the equivalent UI click) with a chosen option that differed from the recommended one, or when a person explicitly modifies a suggested answer, that's precisely the "correction / explicit preference" DESIGN.md wants captured — the same shape of fact ("chose {option} over the suggested {recommendation} when {context}"), the same one-click confirm-before-save discipline, just triggered from a broader set of moments than only a buying mission's final bubble.

**Why it'd help:** memory is one of the product's headline pitches ("cardea remembers your taste across missions") but right now it can only actually learn something from a narrow slice of missions (ones that end in a buying recommendation with a concierge close) — everything else a person decides across a mission is invisible to it.

**Status: shipped, first door only.** The UI-home question resolved to reusing `ApprovalCard`'s own existing anatomy rather than inventing a new sticky-note surface (that fuller DESIGN.md vision — sticky-note clusters near the canvas edge, Edit/Forget controls — is still not built and still parked). Concretely: `ApprovalCard` now tracks whether the open modify form's note came from clicking a listed alternative (`selectAlternative`) versus the freeform "Modify" button; only in the former case does a "Remember this choice" checkbox appear in the modify form, deliberately excluding both a plain "Accept" (no new information, per the entry above) and a hand-typed correction (no clean "chose X over Y" fact shape to extract from freeform text). Checking it and confirming fires the same `/api/memory/promote` call ConciergeClose already used, unchanged shape, just `source: "approval_resolution"` instead of `"concierge_close"` and the fact text built from the real `approval.recommendation`/`approval.category`/chosen alternative — no server-side change needed, `source` was already a free string field. Wired through `mission-layer.tsx` and `board.tsx` exactly like `onResolveApproval`, gated the same way on `live.session.status === "authenticated"`. Live-verified in a real browser (a temporary, uncommitted debug route rendering `ApprovalCard` directly, deleted after): clicking an alternative shows the checkbox, clicking the plain "Modify" button does not, and checking the box then confirming fires `onRemember` with the exact fact text alongside the real `onResolve("modify", ...)` call. Full gate green, no regressions.

## Supermemory is scoped by userId, everything else in persistence is scoped by tenantId

**Not a live leak today, checked precisely, both reasons why:** every one of the four memory routes (`src/app/api/memory/{promote,search,forget,update}/route.ts`) derives identity via `createAuthenticatedMemoryContext()` (`src/app/api/memory/shared.ts`), which calls `requireAuthenticatedUser(client)` against the real server-side Supabase session — never a client-supplied id, not spoofable. And `forget`/`update` go further: both look up the target memory by `{ id: memoryRefId, tenantId }` against the Supabase-side `memory_refs` table *before* ever touching Supermemory, so those two are authorization-checked twice, not once.

**The real inconsistency:** `createAuthenticatedMemoryContext()` returns both a `userId` and a `tenantId` (`tenant = await missionRepository.ensureUserTenant()`, a real Supabase RPC creating/returning the caller's own "Personal" tenant). Every Supabase-side call in the memory routes scopes by `tenantId` (`getMemoryRefByExternalRef`, `createMemoryRef`, `getMemoryRefById`, `markMemoryRefForgotten`, all take `tenantId`). But `src/harness/adapters/supermemory.ts`'s `containerTag(userId)` function builds Supermemory's own isolation key as `user:{userId}` — a completely different identifier, and every Supermemory call (`searchUserMemory`, `promoteUserMemory`) is scoped by that, not by `tenantId` at all. Two different isolation boundaries, on two different storage systems, for what is supposed to be the same account's data.

**Why it's not exploitable right now, and exactly what would change that:** `ensureUserTenant()` currently guarantees exactly one tenant per authenticated user (a "Personal" tenant, created on first use) — so `userId` and `tenantId` are a strict 1:1 bijection today, and Supermemory's `userId`-keyed scoping happens to produce the same isolation `tenantId`-keyed scoping would. The moment that 1:1 guarantee stops holding — shared/team tenants, a user belonging to more than one tenant, any multi-user tenancy concept — Supermemory's isolation silently becomes wrong, because nothing in `supermemory.ts` would need to change for that to happen; it would keep working exactly as written, just now scoped to the wrong boundary relative to everything else.

**Concrete fix:** change `containerTag` in `src/harness/adapters/supermemory.ts` to take `tenantId` instead of `userId`, and update its two call sites (`searchUserMemory`, `promoteUserMemory`) plus `memory-retrieval.ts`'s `retrieveMemoryForContext` (currently takes `userId` in its own input type) to pass `tenantId` through instead, matching what the route handlers already have available from `createAuthenticatedMemoryContext()`. Small, mechanical, no new concept needed — the `tenantId` value already exists at every call site, it's just not the one being threaded through to Supermemory.

**Why it'd help:** closes a real design gap before it ever becomes a real leak, cheaply, while the fix is still small — this is the kind of thing that's trivial to fix now and much more painful to untangle later once real user data is sitting under the wrong key.

**Status: shipped.** `containerTag` now takes `tenantId` and builds `tenant:{tenantId}` instead of `user:{userId}`, threaded through `supermemory.ts` (all three live calls), `memory-retrieval.ts`, the one real call site in `functions.ts`'s `planMission` (`data.tenantId` was already sitting right there on the event payload, no new plumbing needed), and the three memory API routes that called through with `userId` before. No pre-existing promoted memories exist yet in the live deployment (checked), so no migration was needed. Full gate green, deployed.

## Sept 1 sweep leftovers: findings confirmed real but deliberately not fixed before the deadline

**Where these came from:** the five-audit pre-final sweep (see DECISION_LOG, Sept 1). Everything demo-critical or security-shaped was fixed the same day; these survived triage as real but either needing a product decision, carrying UI risk out of proportion to their value 2 days out, or being post-deadline scope. Each is stated precisely enough to execute cold.

- **Keyboard users cannot pan the board, and focusing an offscreen element does not scroll it into view.** `use-board-view.ts` has pointer/wheel pan only; `board.tsx` adds zoom keys but no arrow-key panning, and the world is CSS-transformed inside `overflow: hidden` so browser focus-scrolling does nothing. Fix: arrow-key panning on the surface plus a focus handler that calls `focusOn` for the focused node slot.
- **Releasing a node drag fires the article's click and flies the camera to the node, undoing the pan you were working in.** `mission-layer.tsx` slot pointerdown starts the drag, `node-card.tsx` onClick selects, `board.tsx` `focusNode` animates. Fix: suppress the click when the drag moved beyond a few pixels. Needs a live repro check first.
- **Approval resolve errors render only under the bottom composer, possibly offscreen from the card, and never auto-clear.** `board.tsx` routes failures into the shared `error` shown by the launcher. Fix: render resolve failures beside the ApprovalCard and clear on dismiss or timeout.
- **Mobile: the wallet dock is display:none under 900px with no other entry point, and there is no pinch zoom (ctrl+wheel only).** DESIGN.md locks a priority-view mobile product that was never built; the desktop canvas simply renders small. Known scope, say "desktop" in the demo script.
- **Workspace tab close buttons are tabIndex -1 with no Delete-key handler; tabs cannot be closed by keyboard.** `workspace-tabs.tsx`.
- **Activity filter chips are All/Nodes/Tools/Evidence/Approvals versus the locked list Plan/Actions/Evidence/Decisions/Errors/Approvals, and the locked minimap/breadcrumbs/Focus tool do not exist.** Unbuilt scope versus DESIGN.md, not bugs; needs an owner decision whether the log or the build changes.
- **Landing nav/CTAs deviate from the DECISION_LOG lock (no "Use cases", no "Watch demo", no secondary "Start a Mission").** Later landing passes likely superseded the lock but the log was never amended; amend the log or restore the items.
- **`listEvents` caps at 500 rows with no pagination; resume helpers and upstream evidence trust it as complete.** Silent once a mission log exceeds 500 events; unlikely at current plan sizes. Fix: page through `afterSequence`.
- **`useMissionDataSource` never disposes the live source on unmount (realtime channel and poll timers persist), and an aborted restore deletes the stored last-mission id.** `use-mission-data-source.ts`: return `runtime.live.dispose()` in cleanup; only clear storage on non-abort failures.
- **The fixture data source resolves approvals unconditionally while the live one refuses without a pending approval.** `fixture-mission-data-source.ts`; fixture-exercised UI never sees the live failure branch.
- **WebMCP registration lifecycle: tools never register if `document.modelContext` appears after mount, and `open_mission` remounts the board, tearing down and re-registering all 13 tools.** Registration failures now log (fixed), but structurally the registration belongs above the remount boundary (BoardMount) with a capability-presence retry.
- **A rapid double-click on an approval's Accept can fire `onResolve` twice before `resolving` propagates.** Server-side the resolve RPC replays on its idempotency key, so this is cosmetic; confirmed low risk, left alone.

**Status: parked, post-deadline.** None block the demo. The mobile line belongs in the demo script now.

- **Outbound companion adapter has the same late-`modelContext` blind spot the inbound tools just had fixed.** `src/webmcp/use-companion-tools.ts:100-107` reads `document.modelContext` inside a `useMemo` keyed only on `origin`, so an API injected after hydration leaves that adapter pinned to null, reporting "unsupported" forever. Deliberately not fixed in the Sept 1 sweep: it degrades honestly rather than breaking, it does not touch the inbound tools a judge drives, and widening the change two days out was the worse trade. Fix: reuse the bounded `whenModelContext` poll now living in `use-cardea-webmcp.ts`.

- **A forgotten memory can be re-promoted, because forget hard deletes the provider document.** `POST /api/memory/forget` calls `supermemory.documents.delete(externalRef)`, so the document is gone, not tombstoned. `POST /api/memory/promote` then calls `supermemory.add` FIRST, gets a brand new document id, finds no matching `memory_refs` row (rows key on `externalRef`, the provider id), and inserts a fresh `promoted` row. The forgotten-row conflict branch in that route is therefore unreachable after a real forget. Consent is still explicit on every promotion and forget still erases what it was asked to erase; what does not hold is the stronger "a forget makes this text permanently unsavable" guarantee. Fix: persist the derived deterministic `customId` alongside `externalRef` (it survives the document's deletion, so the two can be joined), look it up BEFORE calling the provider, and refuse when a forgotten row exists for it. That is a schema change plus a repository method, deliberately not attempted two days from the deadline. The route comment now states the gap instead of claiming the guarantee.

- **Route `requestUserInteraction()` to Cardea's own approve button instead of a native dialog.** Shipped on Sept 1 and backed out the same day. The W3C draft passes an agent handle into `execute` carrying `requestUserInteraction()`, and we routed `approve_mandate` and `resolve_approval` through it with a `window.confirm`. It verified correctly against a fake client (confirm proceeds, decline blocks), but in the real ChatGPT browser the primitive exists while the dialog is suppressed, and a suppressed `confirm()` returns `false`, which is indistinguishable from a genuine "no". Every approval came back `declined_by_user` and no mission could ever be approved: the flagship flow was dead in the primary judging environment. Reverted, because a gate that cannot tell refusal from silence is worse than no gate. The correct implementation is not a native dialog at all: Cardea already has a visible approval surface (the mandate sheet's "Approve the mandate" button, and the approval cards), so the callback passed to `requestUserInteraction` should resolve when the person clicks that real control, and reject or time out otherwise. That needs a promise wired to the existing UI plus a timeout policy, which is real work and was not worth attempting two days out. Lesson worth keeping: a fake client cannot tell you how a real one handles a primitive it only partially implements.

- **A buying mission cannot end on a real cart, because the planner cannot chain a step onto an earlier step's output.** Tried and reverted on Sept 1. `shopify.cart_prepare` needs a numeric variant id, and that id only exists after `shopify.product_details` has actually run. The planner is explicitly forbidden from planning such a step by an existing rule that is correct and should stay: "Inputs a capability needs must exist at planning time. Record and id lookups keyed by another step's output cannot be planned: the value does not exist yet and the step will fail at execution." So every buying mission ends on a written comparison and a product page rather than a cart. Adding a planning rule that asked for the cart anyway was measured against the real planner and made plans strictly worse: it produced seven nodes including one with no capabilities at all, where the unmodified prompt produces a clean four. Reverted. The scraping alternative was also measured and rejected: `?variant=` appears 1206 times on a single real Thuma product page, one per colour and size, so picking one from scraped HTML would silently build a cart for the wrong product, which is a worse failure than showing a product page. The real fix is output chaining in the plan: a capability input that references a prior node's recorded output, resolved at execution time rather than at planning time. That is a genuine planner and execution feature, not a prompt change. Until it exists, the honest framing is that Cardea researches and recommends, and the cart handoff is a capability an agent can call directly but a plan cannot pre-wire.
